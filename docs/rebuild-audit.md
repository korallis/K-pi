## GraphAudit

The owned graph runtime is reusable, but currently executes static topology over mutable run files rather than protected, versioned intent. Critical defects include premature durable DONE, model-asserted evidence, stale-release authorization, unsafe partial-action replay, lost downstream work after sibling failure, and unrecoverable advertised resume paths. Read-only source audit completed; no validation or writes performed.

runLoop compiles a Task, snapshots inputs/worktree and loads a named JSON graph; GraphEngine executes bounded batches through owned createAgentSession or a per-review BackgroundBus, merges assignments, refreshes driver facts and routes. Graph checkpoints persist execution state; state.json separately persists product status/progress/repair history. resumeLoop reloads mutable task/topology plus both persistence streams. driveJob independently handles human gates and ship verification, but currently publishes DONE before that final verification.

## Prioritized repairs and predicted failing scenarios

### P0-1 — Completion authority publishes DONE before completion verification
**MODIFY L:453–454, 1725, 1952, 2239–2310, 2335–2336; DELETE graph release.set status assignment.** stateDocument infers product DONE from graph completed. driveUntilPause persists that state before driveJob calls finalizeShip; the human submit path can do the same. A subsequent crash leaves durable DONE, and resumeLoop immediately returns DONE without checking commit, delivery or receipts.
**Scenario:** ship returns without a valid commit, or creates a commit but no PR; terminate the process after the completed-graph write and before finalizeShip finishes. Resume silently accepts DONE. Even without a crash, live readers temporarily lose job/policy ownership during finalization.
**Gate:** only one independent completion transaction may publish DONE, after verified intent revision, candidate/evidence/review/release and configured delivery all agree. Graph exhaustion is not completion. Conflicts with docs/spec.md:339 (DONE definition) and PRD AC-04.5 at docs/PRD.md:137.

### P0-2 — Evidence is model testimony, not independently executed receipts
**REPLACE L:evidencePasses:1006–1035 and tester publication path E:1078–1154 with runtime-owned evidence collection/verification; KEEP receipt-backed reviewer publication seam.** evidencePasses requires merely some command records whose latest exits are zero plus claimed passing required IDs. It never requires task.quality_gates or check.cmd to appear, never evaluates expected exit/stdout, accepts a true AC duplicate even if another entry says false, and does not link reports to tool executions. The tester is readOnly:false and returns assistant JSON; it is not the REQ-RS-06 write_contract publisher.
**Scenario:** tester executes nothing, emits head=current HEAD, commands=[{cmd:'true',exit:0}], ac_results containing required IDs with passed:true. Schema passes and test.passed becomes true. Conversely a legitimate criterion expecting exit 1 is rejected if that receipt is reported correctly, because every exit must be zero.
**Gate:** collected operation receipts mapped one-to-one to required checks and exact expectations; verifier and implementer cannot synthesize their own success authority. Citations: docs/PRD.md:111,135–136,180; docs/spec.md:180,245–257,318,440–448. Existing fixture test/gated-loop.test.ts:246–272 optionally runs real commands but always constructs evidence independently; it does not prove receipt provenance.

### P0-3 — Approval and freshness are not bound to the candidate about to ship
**MODIFY L:1370–1372, E:1730–1774 submitHuman, G/coding-loop.gated.json:555–584, G/coding-loop.auto.json:521–544, L:2273–2309.** Fresh means only evidence.head == HEAD. Dirty product edits do not change HEAD. After review, human/release.set outgoing routes only check approval and prior shipping; refreshed bounds/test/freshness are not rechecked there. driveJob checks release.approved plus shipping, not final AC/bounds/review truth. Verdict schema also permits approved:true with status:BLOCKED and nonempty blockingIssues; auto happy-route only tests approved.
**Scenario:** green review reaches release dialog; modify an allowed product file so tests fail, then approve. HEAD remains unchanged, ship commits untested bytes. Or modify an out-of-bounds file while the dialog is open: submitHuman refreshes bounds=false but still follows human→ship.
**Gate:** approval must name intent revision, exact candidate/tree digest, evidence bundle and review decision; any relevant mutation invalidates approval before dispatching irreversible work. Require coherent verdict semantics. Existing HEAD-only spec at docs/spec.md:257 is itself insufficient for the user's stronger independent-evidence mandate; even the existing release invariant in PRD AC-04.2/docs/PRD.md:134 is not held at dispatch.

### P0-4 — Ship replay retries the whole action after a partially successful commit
**MODIFY E:1283–1351, L:1627–1646, 2008–2039 and ship graph nodes into resumable operation phases.** Idempotence is checked on edges entering ship, not before each ship prompt/retry or when restoring directly into ship. A transient failure after git commit retries the full prompt in the same threaded session. A kill after commit but before checkpoint restores active ship and dispatches it again. Finalization detects duplicate commits only afterward.
**Scenario:** ship commits successfully, then provider transport fails before the node returns; the next prompt again requests exactly one commit. With a subsequent small file change or permissive commit command it can create a second job-trailer commit, then pause with ambiguity. Successful commit followed by failed push/PR also becomes operator delivery work rather than resumed remaining operations.
**Gate:** durable operation identity and phase receipts for stage/commit/push/PR, reconcile real Git/remote state before repeating; retries must resume remaining actions, not replay a monolithic prompt. docs/spec.md:466 explicitly requires idempotent ship/commit. Existing delivery-resume tests test/gated-loop.test.ts:699–797 cover finalized graph→operator-repaired PR, not a kill/429 inside ship.

### P0-5 — Task/AC protection is advisory and unversioned
**MODIFY R:255–294, 333–361, L:2327–2340, 2398–2451; separate current_module_id into execution state.** contractHash hashes the currently supplied task, not an immutable authorized version, and uses insertion-order JSON.stringify rather than canonical form. No task hash is stored/checked by graph restore or completion. resumeLoop trusts edited mode/AC; in-flight policy and implement reread task while loopFacts retains the original task object. Reserved artifacts in policy.ts:388–395 include only verdict.json, release.approved and ship.json, not task/state/evidence/checkpoints. Default bounds may incidentally block task writes, but protection disappears under broad allowed paths; it is not an invariant.
**Scenario:** pause after review, edit task.acceptance or mode, then resume. No explicit intent-change violation is checked at release/completion. Or authorize broad writes covering .kpi/** and have an implementer change its own task bounds; policy reads the changed contract while evidence evaluation still uses the earlier one. Reordering task object keys also falsely stales hash-bound research/stack.
**Gate:** append-only authorized intent revisions; explicit approval of amendments; every execution/evidence checkpoint refers to one protected revision; dynamic slice/strategy changes must not rewrite intent. Conflict with docs/PRD.md:127 AC-03.4. docs/spec.md:354 additionally tells operators to widen task bounds but defines no authorization/version transition: reconcile this with the mandate rather than retain raw edits as recovery.

### P1-6 — Successful siblings lose their downstream work on failure/stop
**MODIFY E:1621–1648, 1659–1677 and persisted activation state.** Rejected batches commit successful siblings and remove them from active, but never route their outgoing edges. Restore runs only unresolved nodes; successful siblings' descendants disappear permanently. routedPause similarly discards normal sibling targets in favor of one pause's static resume list.
**Scenario:** fan→A and B; A succeeds and has A→C; B fails. Checkpoint marks A completed and resumes B only. C never executes. Existing test/resume.test.ts:706–794 has successful and failed leaf siblings, so it proves the side-effect counter but misses lost descendants. The same omission affects the interrupted second-batch case at test/resume.test.ts:147–240.
**Gate:** persist completed results plus pending edge/activation propagation in the same transaction, preserving all outstanding branches. Conflicts with docs/spec.md:457 (superstep commit semantics),463–464 (unresolved-only/sibling-preserving restore).

### P1-7 — General DAG/readiness semantics do not exist; cycles can run without progress supervision
**MODIFY E:874–907,1473–1678; S:136–143.** Active is simply last step's target set. There are no dependency counters/activation IDs. Unequal-length fan-in executes a downstream node too early and possibly repeatedly. Any no-outgoing node implicitly completes. A cycle of set/agent nodes without node IDs test/review is not observed by L's no-progress detector and runs indefinitely. Pause-as-entry is accepted, then execution throws a generic contract error rather than parking. Reserved __end__ is not excluded as an actual node ID.
**Scenarios:** root→A→join and root→B→C→join runs join while C is executing, then again; set A→A repeats forever with no verifier/progress witness; remove outgoing edges from a required node and graph exhaustion is treated as completion.
**Gate:** explicit work-item dependency/activation semantics, required-goal coverage and progress/recovery for all execution branches. Do not reintroduce time/round caps; bounded concurrency remains useful. docs/spec.md:20 calls this a DAG runner, while §7 deliberately contains repair cycles—model these as goal/work transitions instead of relying on the label DAG.

### P1-8 — Checkpoints are neither whole-run transactions nor protected execution versions
**MODIFY E:843–849,664–745,1790–1799; L:1654–1725,2312–2396.** Graph state is checkpointed before repair history/state.json, with repair.json/task mutations in between. A crash can preserve a routed plan but lose verifier count/replan allowance/brief. No initial checkpoint exists before the first superstep; a kill in the initial ac-compiler leaves a run that resume cannot restore. Restore binds only graph ID/job ID plus limited budget shape; it reloads whatever same-name graph currently exists. No topology digest/version/migration record is persisted. All non-running/non-interrupted/non-completed statuses are treated as rearmable, even unknown statuses. Exactly-six-digit checkpoint discovery ignores checkpoints once superstep reaches 1,000,000.
**Scenarios:** change a project graph edge under the same id between stop/resume and execute a different workflow with stale approvals; delete/rename an active node and resume throws; kill between graph route-to-plan checkpoint and recordNoProgress and lose repair state; kill the first prompt before any checkpoint; long set cycle crosses six-digit range and restore selects older state.
**Gate:** committed execution revisions plus atomic state/progress/outbox transaction, validated checkpoint schema and intentional migrations, durable initial run state before dispatch. Keep atomicWrite itself; it protects one file, not these multi-file invariants. docs/spec.md:462–466; PRD AC-14 observability and AC-05 resumability.

### P1-9 — Frozen-plan and specification nodes have no executable artifact/result contract
**REPLACE transcript-only nodes; MODIFY G/coding-loop.gated.json:61–77,244–247; auto plan-check; G/spec-first.json:5–25.** plan-check has no response: “this plan is stale” and “it is valid” are equally successful empty assignments. Existing frozen-plan test test/gated-loop.test.ts:837–864 asserts snapshot/skip behavior only, not successful implement/ship or stale-plan routing.

## Necessary invariant gates versus ceremony

**KEEP:** unauthorized intent/permission changes require genuine authority; exact candidate/evidence/review linkage; independent reviewer capability; executable checks and coherent required-AC coverage; product writer exclusivity; response schema/path/role validation; bounded concurrency; operator stop; idempotent irreversible effects; atomic publication. Schema validation and Dune checks are valuable only insofar as they enforce those real ownership/integrity constraints.

**MODIFY/MERGE:** retain one owned GraphEngine and native sessions. Consolidate graph checkpoint, product status, repair history and side-effect reconciliation into one authoritative transition model. Stable goals/acceptance must be separate from dynamically replaceable execution topology, slice, role dispatch and retries. A graph edit should be an explicit execution revision, not rereading mutable JSON at restart. Initial coding-loop JSONs can seed strategies, not define immutable mandatory ceremony for every task.

**REPLACE/DELETE ceremony:** ac-compiler/specify/plan-check model turns that cannot publish or affect a contract; status=DONE as graph data; fixed “two replans then ask the user” as the only progress recovery; human repair demands for formatting/schema/stack/service hiccups the runtime can repair; booleans that claim authorization without enforcement. Do not remove genuine authority barriers merely to keep a run moving. Role-quality selection must stay separate from account authorization/scheduling; current E:994–995 simply inherits parent model/thinking for every in-process node and E:1190 forwards the same label to reviewer.

## PeersAudit

The bus is a parent-owned collection of local K-π RPC child processes, not a peer runtime or a bus.jsonl transport. Workers retain a session only while their owning parent/bus lives; they cannot address one another, join rooms, replay messages, or reconnect after restart. A concrete source-level defect prevents communicate from waking an idle worker: it sends queue-only steer/follow_up commands. The owned fork already supplies durable sessions, prompt/steering, event subscriptions, RPC, tool allowlists, and lifecycle primitives; preserve these and replace the bus's ownership/delivery bookkeeping rather than introducing another orchestrator or external Pi dependency.

Current: built-in kPi extension → parent tools' private Map<job, BackgroundBus> OR graph node's separate BackgroundBus → owned CLI child with immutable environment descriptor and JSONL stdin/stdout RPC → AgentSession + persisted session JSONL. Child tools publish role contract files and receipt files; parent waits for agent_settled then polls disk. Separate process-local sets expose node/worker presence. bus.jsonl is write-only metadata history in this path, not a transport or recoverable inbox.

## Actual agent and communication model

1. **Launch and identity.** `BackgroundBus.spawn` creates a fresh `role-UUID`, fresh session path under `agents/`, and descriptor for each spawn; it snapshots quality gates and optional publication capability (`spawn.ts:440-533`). `launchWorkerProcess` launches this repository's CLI with `--mode rpc --session ... --session-dir ... --tools ...`, same cwd, inherited environment plus descriptor, no shell (`launch.ts:115-140`). The spawn event means OS process creation; successful initial RPC prompt preflight subsequently supplies real session acceptance (`spawn.ts:556-569`; `rpc-mode.ts:394-415`). Identity parsing constrains role/tools/job path and caches the validated descriptor, but is not registration against a durable live-peer authority (`identity.ts:126-230`).
2. **Model and tools.** Role tool ceilings are real, and CLI/SDK explicit allowlists are supported (`roles.ts:20-26,97-113`; `sdk.ts:65-77`). Parent spawn simply forwards caller `model`; absent a model, the child follows normal CLI/session defaults. No K-stack role-map resolution occurs here (`communicate.ts:419-424`; `spawn.ts:523-532`; `launch.ts:130-132`). Graph worker launch forwards `this.modelLabel()` (`engine.ts:1188-1194`). ResourceAudit owns the routing redesign.
3. **Lifetime.** An RPC worker stays alive waiting for stdin after its first turn (`rpc-mode.ts:819-822`), but the owning parent stops it on every `session_shutdown` (`communicate.ts:595-605`), including reload/new/resume/fork reasons represented by `core/extensions/types.ts:643-647`. Graph reviewers are intentionally one-shot: new bus and worker per node, stopped in `finally` (`engine.ts:1176-1251`). On owner process death, its pipes close; RPC EOF explicitly disposes the runtime and exits (`rpc-mode.ts:727-818`). Persistent transcript is not persistent peer ownership.
4. **Addressing.** Only parent sessions register `communicate`, status, spawn and stop. Workers register only `write_contract`, `claim_path`, `release_path`; role allowlists omit all communication tools (`communicate.ts:58-64,106-230,430-467`; `roles.ts:20-26`). Parent lookup spans its own jobs, but only its private `buses` map (`communicate.ts:288-289,313-344`). The graph bus registry used by `/agents` is a separate observational registry, not reachable by that lookup (`sessions-snapshot.ts:62-80`). Seeing a graph worker does not make it addressable through parent `communicate`.
5. **Delivery and ACK.** Initial work uses RPC `prompt`; subsequent messages always use RPC `steer` or `follow_up`. `expect:none` waits for local pipe write/backpressure, then explicitly returns `accepted:false`; `expect:ack` waits for command success, which means queued, not consumed or durably recorded (`spawn.ts:640-655`; `protocol.ts:264-286`). All settle waiters resolve on the next `agent_settled`, without delivery correlation (`protocol.ts:177-186,299-330`).
6. **Persistence and completion.** `logMessage` logs target, mode and expectation, but neither message text nor sender/message ID; logging happens before transport delivery (`spawn.ts:340-369,624-635`). `bus.jsonl` cannot reconstruct a message and is not read by the delivery implementation. Reviewer/tester completion uses role-specific shared files plus per-worker publication receipts; writer completion is changed candidate bytes plus ladder validation (`spawn.ts:657-695,754-820`; `write-contract.ts:146-208,286-334`). Files are polled at 50ms intervals; publications are not pushed back as correlated durable result events.
7. **Presence and ownership.** Presence is process-local rows plus child/PID liveness, not online/busy/idle/disconnected/restarting state. `lastEvent` only advances for limited bus actions; worker model is not in the live-worker projection (`spawn.ts:399-410,581-601`; `sessions-snapshot.ts:107-121,181-198`). Worker/writer admission is process-wide, but not checkout-wide across processes (`spawn.ts:36-39,64-113,136`). Path leases are job-directory files, protected through a polling lock and PID checks (`leases.ts:125-199,242-269`).

## Source-backed defects and concrete failing scenarios

### P0 — Idle peers acknowledge but do not run
`WorkerProtocol.deliver` always sends queue-only commands (`protocol.ts:281-286`); RPC invokes `session.steer/followUp` (`rpc-mode.ts:418-425`), which only enqueue (`agent-session.ts:1409-1473`; `packages/agent/src/agent.ts:283-289`). **Scenario:** spawn explorer, let initial work settle, communicate a second request with `expect:ack`: it reports acceptance, but no second turn starts. `expect:result` to an idle reviewer waits until timeout. Graceful stop to an idle worker also queues unexecuted work before eventually clearing it. The existing correct wake primitive is `prompt` with `streamingBehavior`, or `sendUserMessage` which calls it (`agent-session.ts:1572-1603`). Use that single atomic path, not a racy get_state-then-select workaround.

### P0 — No peer-to-peer, room, replay or restart contract exists
Workers have no communication endpoint; parent maps disappear on restart; persisted session paths are never restored into BackgroundBus. `bus.jsonl` lacks payload, origin, message IDs, sequence or ACK cursor. No rooms, subscriptions, reconnect, heartbeat or restart implementation appears in the fully inspected bus directory; alternate lookup of room/replay/restart/sender/recipient/sequence finds only the documentation prohibition on external room packages. **Scenario:** A sends B an update while C is disconnected; neither direct worker send nor room fanout can be expressed, and restarting C cannot replay it. With three background peers the hard-coded cap rejects the third (`spawn.ts:36-39,76-79`). Parent plus two workers is possible but is not three peer workers.

### P0 — Ownership protection is incomplete
- `claim_path` acquires ownership, but mutation dispatch never checks that a lease is held (`communicate.ts:242-284`; `policy.ts:795-809`). **Scenario:** an implementer directly calls `write` on an allowed path without claiming it; the claim-before-edit rule is not enforced.
- A narrowed implementer/arena tool list containing only `bash` is classified non-writer, while its shell lacks the reviewer/tester/explorer restrictions (`roles.ts:8,20-26,111-113`; `communicate.ts:242-284`). **Scenario:** launch a normal writer plus an implementer narrowed to read/bash; the latter can attempt allowed shell mutations without occupying the writer slot. Mutation authority must include every shell/custom tool capable of writing, not just tool names write/edit.
- Parent mutation exclusion inspects only parent-owned buses (`communicate.ts:370-380,576-592`), not all runtime sessions/graph nodes; admission counts only background workers. Another parent process or graph mutator is outside the exclusion.
- Leases are scoped to run directory, not canonical checkout (`leases.ts:108-114`), so different jobs may separately claim the same checkout-relative path. PID-only lease liveness cannot distinguish a dead worker from an unrelated reused PID (`leases.ts:37-49,252-264`).
- `stopUnlocked` removes the record and releases admission **before** awaiting stop and releasing path leases; stop errors are swallowed (`spawn.ts:913-925`). Another bus sharing admission may launch a new writer while the old writer is still cancelling. Confirm termination/fencing before transferring authority.

### P1 — Assignment and result identity are absent
A fresh publication means merely a publication ID different from the receipt observed before delivery; there is no request/assignment/intent-version correlation (`spawn.ts:663-686`; `write-contract.ts:53-65,298-304`). **Scenario:** concurrently send two result requests to one worker: both wait on the same next settle and can accept the same fresh publication as their own. A result cannot demonstrate which protected intent/execution assignment produced it.

Reviewer/tester outputs share `verdict.json`/`evidence.json` for all same-role workers (`roles.ts:66-69`). **Scenario:** two reviewers publish differing verdicts concurrently; each gets its own receipt, but the later write overwrites the shared contract, making the other receipt fail hash validation. Use immutable per-assignment results with separately selected authoritative projections.

Receipts prove schema-valid publication bytes, not independently executed tests or completion. Writer result checks only changed bytes and `parseLadderDecision`; unchanged correct bytes are rejected even when the new assignment genuinely re-verifies them (`spawn.ts:744-785`). Preserve an independent evidence-completion authority rather than equating worker ACK, settle, publication, or prose with success.

### P1 — Worker identity errors fail open at general tool hook
`registerWorkerTools` catches `resolveWorkerIdentity` errors and returns without blocking (`communicate.ts:220-227`). Worker-specific tool implementations still require identity, but the global role restrictions do not. **Scenario:** invalid/missing-task startup descriptor reaches a core bash/write call under whatever tools the CLI enabled; the worker-specific hook silently abstains. A declared worker with invalid identity must fail closed before session/tool activation.

The descriptor is frozen launch data, not cryptographically authenticated live registration. The capability is also written in receipt JSON (`write-contract.ts:190-207`) in the shared tree; it must not be described as secret from all sibling same-user workers with unrestricted read. It is useful attribution under trusted harness execution, not a sandbox boundary. A rebuilt runtime should own identity and publication authorization outside model-writable records.

### P1 — Worker bounds can follow another job
`kPi` installs the same global `resolveActiveWriteAllow` into every process; it reads `readLiveJob(cwd)`, not the worker descriptor's job/intent (`index.ts:27-39,103`). Policy also resolves global live state, and chat has no job bounds (`policy.ts:581-603,781-790,988-998`). **Scenario:** a worker for job A remains alive while A pauses or another run becomes live; policy may use no bounds or job B's bounds while its identity and contract pin still name A. All tool authority must derive from its versioned assignment.

### P2 — Cleanup and lock races need genuine transition contracts
`launch.stop` waits for clear_queue and abort (each default 30s request timeout), closes stdin, sends SIGTERM, and eventually SIGKILL, but does not await post-SIGKILL exit (`launch.ts:177-207`; `protocol.ts:338-340`). These are bounded transport operations, not a worker/run completion definition. Presence/lease/admission removal must follow confirmed shutdown or fenced incarnation loss.

`withLeaseLock` compares lock bytes, then separately removes the pathname (`leases.ts:163-170,179-181`). **Source-derived race:** two stale-lock reapers both inspect the stale bytes; one removes it, a new owner acquires, and the delayed second removal can unlink the new lock. The compare/read and unlink are not atomic despite the comment claiming removal of only the inspected leftover. A single runtime ownership authority removes this polling/reaping complexity; if multi-process standalone lease mutation remains, it needs a genuinely safe recovery primitive.

## Smallest clean migration seams

1. **One owned runtime service, not another orchestrator.** Place durable peer identity, incarnation, assignment, addressing and delivery ownership in the existing fork's runtime lifetime, above replaceable sessions. Inject it through the built-in registration (`extensions/index.ts`) and graph worker seam. Replace private per-extension/per-node maps; make `/agents` a projection, not a second source of truth. Stable peer ID must survive session reload and runtime restart; transport connection and process PID are replaceable incarnations.
2. **Reuse sessions directly.** `createAgentSession` already accepts `sessionManager`, canonical model runtime, explicit tools/custom tools; `SessionManager.open` restores a named transcript. Persistent in-process peers can use event subscriptions plus `sendUserMessage`. Where process isolation is wanted, keep owned CLI RPC but let the long-lived runtime own pipes; do not tie child lifetime to the operator session. Reopening persisted sessions after runtime restart is a supported primitive, but restoration of assignment, inbox and authority must be implemented above it.
3. **One transport implementation.** Merge WorkerProtocol's bounded framing/backpressure/redacted diagnostics with RpcClient's typed commands, general event subscription and process/stdin error handling. Neither is a complete replacement unchanged: base client start uses a 100ms sleep and its outbound send ignores drain (`rpc-client.ts:133-140,588-599`); bus transport lacks a general trusted publication/peer-event path. Use RPC prompt with streamingBehavior for delivery. Keep transport failure bounds, without turning deadlines into successful completion or arbitrary autonomous-run caps.
4. **Authenticated realtime message envelope.** Add stable message ID, sender/recipient or room, peer incarnation, assignment/intent reference, durable sequence and reply/result correlation. Runtime derives sender from authenticated connection, not model-selected parameters. Append durable inbox/outbox/room events before reporting durable acceptance; deliver by events/pipes, not filesystem polling. Distinguish accepted, queued/delivered, processed and result. Replay from per-peer cursor; duplicate deliveries must not repeat externally visible mutations/publications.
5. **Rooms and direct addressing through the same service.** Register communication tools for every authorized peer. Room membership, live fanout, offline replay and direct sends use one ordered event authority and one address book. Remove active-job lookup as the fallback meaning of an unknown agent. Do not require an operator to relay messages or introduce separate room package/orchestrator.
6. **Publication and authority.** Retain canonical path, schema validation, atomic storage and content hashes. Move publication authorization and result recording to trusted runtime dispatch; notify parent/consumers on durable publication rather than polling. Bind each result to assignment, protected intent version and evidence references. Use per-assignment immutable paths and host-owned projection of current verdict/evidence.
7. **Ownership gates in dispatch.** Canonical checkout/path scope, fenced owner incarnation and assignment-derived bounds must protect every actual mutation path. Treat shell mutation capability honestly. Release/transfer only after completion/cancellation fence. Keep human approval only for named irreversible actions/authority changes; do not retain parent hierarchy, per-node process teardown, fixed two-peer ceiling or manual relay as ceremony masquerading as safety.
8. **Documentation clean cutover.** Replace `docs/agents-bus.md` and `MECHANISM_SENTENCE`. Current docs say processes talk over bus.jsonl; actual transport is pipes. They also claim same-process sendUserMessage and role-map selection as existing bus paths, neither implemented by BackgroundBus. Existing wireframe/cap prose must not limit the new autonomous peer contract.

## Necessary invariant gates versus ceremony

**Necessary:** protected intent/assignment binding; authenticated sender and incarnation; bounded transport memory; durable acceptance/replay cursor; idempotent publication; concrete mutation ownership enforced at the operation; authority fencing on restart; independent evidence acceptance; irreversible-action authorization; confirmed cleanup transitions.

**Keep but redesign:** schema/path/hash publication checks, atomic persistence, canonical path resolution, role capability ceilings, single-writer safety for shared mutable checkout, request correlation and cancel-queue-before-abort ordering.

**Delete or merge as ceremony/incorrect authority:** forced one-shot worker teardown, parent-only messaging, fixed N≤2 peer count as a product rule, graph-versus-tool bus tables, duplicate RPC framing/client policy, 50ms contract polling, transcript prose as diagnostics promoted into decisions, global active-job selection for worker permissions. Thread count/resource scheduling may still be operational policy, but must not replace correctness gates.

## Meaningful three-agent live smoke scenarios (not run)

Use A implementer, B tester, C reviewer as three runtime peers, with authorized independent roles and a disposable checkout. Current code cannot launch all three as background workers without changing the hard two-worker cap; record that as a present blocker, not silently substitute parent plus two workers.

1. **Idle direct wake and room fanout.** Let B and C settle; A sends B a direct test request and room progress to B/C. Observe actual new turn at idle B, authenticated A origin, both room deliveries, unchanged peer IDs/session histories, and no operator relay. Exercise steer during a real tool and follow-up during streaming separately; observe ordering, not merely ACK strings.
2. **Disconnect, replay and duplicate suppression.** Disconnect C after message acceptance but before processing; A/B continue exchanging room messages. Restart C with the same peer ID/new incarnation, replay only its unprocessed sequence, and confirm each durable result/effect occurs once. Restart the owner runtime as a separate variant; reopen sessions and reconstruct pending deliveries without reading/polling bus files for arrival.
3. **Fenced ownership and independent completion.** A claims a canonical path; B and C cannot mutate it through write/edit/bash/custom tools or forged sender data. Stop/crash A during a tool, transfer only after fencing, and attempt stale-incarnation write. A's claim that tests pass, its changed candidate file, and a stale verdict must not complete the assignment; B produces fresh execution evidence and C publishes a review bound to the same intent/revision.
4. **Overlapping messages/publications.** Send B two distinct assignments before settlement and have B publish separate correlated results; neither may satisfy the other request. Run two review assignments with different outputs and ensure no shared verdict overwrite. Change active operator job while all three stay alive; their authority remains pinned to their original assignments.
5. **Ownership versus session lifetime.** Reload/switch the operator session while A/B/C are idle and while B tests. Peers remain addressable and room membership remains intact. Explicit peer stop cancels queued work, terminates the intended incarnation, records presence transition and frees ownership only after termination/fencing. No stray process survives final runtime shutdown.

## 2. Genuine defects and concrete failing scenarios

### A. Account selection is outside the real credential boundary — highest priority
1. **Codex sibling rotation does not change the wire credential.** accounts/index.ts:856-935 changes headers only. ModelRuntime.prepareRequest first resolves primary auth and later retains resolution.auth.apiKey (core/model-runtime.ts:581-605). Codex extracts accountId from options.apiKey (api/openai-codex-responses.ts:255-275); buildBaseCodexHeaders applies additional headers then unconditionally overwrites Authorization and chatgpt-account-id from that primary credential (:1593-1612). Scenario: primary account A reaches quota, balancer selects B and records B, but the real request is still authenticated as A. Both attribution and availability decisions become false.
2. **A healthy pooled-only credential cannot bootstrap a request/model.** Key-only /accounts login returns a Credential directly rather than modelRegistry.login (accounts/index.ts:226-234), then persists it only through the account store (:302-314). Native prepareRequest throws when primary getAuth is absent BEFORE the account hook; setModel additionally requires native configured auth (core/model-runtime.ts:581-593; agent-session.ts:1678-1680,2635-2638). Scenario: add the first z.ai/OpenAI API-key slot through /accounts without an existing env/auth.json credential; the slot exists but the runtime cannot use it. A revoked primary OAuth grant similarly prevents a healthy sibling from reaching the hook.
3. **Exhausted-pool handling is not fail-closed.** When no slot is available, the hook nulls only headers already present (accounts/index.ts:890-899); primary options.apiKey remains intact, and Codex recreates Authorization regardless. Also a selected nonlocal slot whose secret is missing leaves primary authentication untouched (:912-934). The extension runner catches hook failures and proceeds with existing headers (core/extensions/runner.ts:1099-1130). Scenario: all Codex slots cool, account JSON read fails, or a pooled secret is absent: the primary account may still be sent traffic, outside the purported scheduler decision.
4. **Mixed credential kinds do not control native request shape.** Anthropic chooses OAuth identity/beta headers, tool-name mapping and request shape from primary apiKey, not the selected slot header (api/anthropic-messages.ts:551-568,928-970). Scenario: primary API key plus selected OAuth slot sends OAuth credential with API-key-mode preparation. Move whole selected credential resolution, not just its bearer string, before the native adapter.

### B. Health, ownership and failover
5. **Health and affinity vanish on restart and are independent between peers.** AccountBalancer.cooling/sticky/cursors are Maps (balancer.ts:49-54); UsageCache.snapshots is a Map (usage/cache.ts:19-31); each registerAccounts constructs its own instances (index.ts:553-563). needsLogin is durable, cooldown is not. Scenario: account A is known cooling in one process, then a peer or restarted session selects A again. This is a missing persistent-runtime mandate feature as well as a practical multi-session scheduling hazard.
6. **Pooled credential refresh races across processes.** AccountsStore.mutate serializes only one store instance (store.ts:311-348); writes are individually atomic but secrets/accounts are two separate writes (:383-403,626-637). Every process refreshes nonofficial expiring slots independently (index.ts:623-660). Scenario: two peers read the same rotating refresh token, both refresh it, one receives invalid_grant and marks a usable resource needsLogin; simultaneous read-modify-write can lose another slot update. Native auth storage already supplies process-safe locking; merge ownership onto that mechanism.
7. **Local transport failure never becomes local health.** Classification accepts 429/402/quota-shaped 403/400 only (errors.ts:97-110). An assistant error with no attributable response only recognizes invalid_grant (index.ts:1016-1036). Scenario: local server refuses connection; its slot never cools despite spec.md:732. The test named 'unreachable local server cools' explicitly calls balancer.markCooling itself (test/local-providers.test.ts:257-274), so it does not exercise this missing path.
8. **Endpoint pinning overrides local health and defeats same-pool failover.** before_provider_headers selects healthy slots, then replaces that choice with the first endpoint-matching local slot without checking health/needsLogin (index.ts:869-880). planFailover treats every same-pool sibling as the same model and changes no model endpoint (balancer.ts:242-245). Scenario: model M was discovered on local server A; A cools and B is selected, but the next header hook pins A again because M.baseUrl still names A. B may not serve M at all.
9. **Exact-model fallback bypasses local/cloud authorization rules.** preferredModelSlugs is iterated directly, never through poolOrder (balancer.ts:248-263 versus :294-314). Setup proposes fallback_models from all configured candidates (models.ts:94-96,325-337). Scenario: accept a generated map containing local and cloud candidates; a local request can escape to a paid cloud resource, or a cloud request can select a local pool, without /pool chain or explicit pin. This conflicts with spec.md:730. Keep a separate authorised-resource boundary beneath model preference.
10. **Legacy fallback stops at a family with no usable model.** The non-model-order path selects one next pool and only then looks up its model (balancer.ts:265-280). Scenario: next configured family has a healthy slot but no available model while a later family has both; plan carries no model, applyFailure cannot move and never examines the later family (index.ts:736-744). spec.md:760 requires skipping unavailable model families.
11. **Successful low-quota responses can strand the last usable seat.** after_provider_response proactively calls applyFailure for <=5% even with no successor (index.ts:955-972); applyFailure cools first and returns false when no plan exists (:716-730). Scenario: sole account still has 4% allowance; next request is considered unauthorised rather than continuing or deliberately waiting. The pure balancer test says a lone 5% slot retains its pin (test/accounts-routing.test.ts:103), but the integration path differs.
12. **Quota freshness/reset semantics are wrong in places.** UsageCache.remainingPercent never consults observedAtMs/resetAt (usage/cache.ts:33-39), so reset windows leave stale ranking. readUsageHeaders parses numeric Retry-After using generic epoch parsing (usage/headers.ts:121-142,180-184), unlike errors.ts:80-86 which correctly treats it as relative seconds. Scenario: 200 response with low remaining and Retry-After: 60 yields a 1970 reset time and ineffective proactive cooldown. Rate-limit capacity is also flattened into the same percentage as subscription allowance, with no dimension distinction.

### C. Role/model catalog correctness
13. **Saved roles do not route actual workers.** resolveRoleModel/resolvePanel have no production consumers in src (only definitions in models.ts:197-209); fallback_models alone is consumed. PeersAudit corroborated communicate.ts:419-424 → spawn.ts:522-532 → launch.ts:130-132 forwards explicit model only; omitted model uses child CLI defaults, and graph worker dispatch uses parent modelLabel. Scenario: apply frontend/reviewer role choices in setup; launched workers do not use them. Clean cutover must migrate the real dispatch boundary, not add a second orchestrator.
14. **'Healthy live candidates' is only pool-name membership plus slot count.** liveCandidates compares model.provider literally to POOL_IDS/configuredPools (models.ts:36-65); setup only checks slots.length (:313-320). llama.cpp is excluded because its pool is llama. A pool containing only needsLogin slots is included if primary native auth remains configured. No account entitlement or cooldown filter is applied.
15. **Ladder prose has executable semantic drift.** parseModelLadder extracts only backtick patterns (ladder.ts:50-63,90-98); suggestForRole uses substring inclusion (:174-185). Therefore implementation preference 'glm-5.3 (not flash)' still matches flash, and fast-role 'any local' never becomes a pattern (docs/model-ladder.md:19,23). UI-conditioned panel language has no task input. Working-order normalization 'Claude Opus 5' becomes claude-opus-5 and does not match a typical claude-opus-5-* slug with different version spelling if naming diverges; retain exact observed identifiers rather than assume prose normalization is a capability schema.
16. **Provider prefix is not independent model family.** suggestPanel deduplicates slug.split('/')[0] (ladder.ts:160-162,242-257). Scenario: anthropic/Claude and cursor/Claude count as two families, while distinct model families served by one proxy count as one. Manual edits/writes enforce only membership and panel cap, not independence or even unique entries (models.ts:119-135,267-271). spec/kstack.md:195 requires diverse review; there is no runtime reviewer-independence gate.
17. **Empty setup and weak role parsing can preserve stale routing.** No candidates causes an 'inherit' notification and return without replacing an existing map (models.ts:321-324). readKStackModels accepts roles:null or an array because typeof roles === object (:185-189), permitting crashes/bad types at role access; setup writes validate slugs but runtime reads do not validate required value shapes. Scenario: remove all resources then rerun setup; old fallback_models remain, despite the inheritance notification.
18. **Local refresh loses healthy cached origins during partial failure.** refreshLocalModels accumulates only successful origins; once any server answers, it writes the discovered list and drops cached entries for unavailable siblings (local/providers.ts:282-323).
